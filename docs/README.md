# OctoAcme Project Management Docs

This README provides a quick entry point for the project management guidance used by OctoAcme and links to the core process documents in this repository.

## Project management process summary

OctoAcme follows a lightweight, cross-functional project lifecycle that begins with initiation and ends with continuous improvement. Each initiative starts by confirming the business problem, identifying stakeholders, creating a one-pager, and deciding whether the work is ready to move into planning. Once approved, teams define scope, milestones, dependencies, and success metrics so the work has a clear foundation before execution begins.

During execution, the team uses a simple delivery structure built around backlog prioritization, iterative delivery, and visible tracking. Work is organized on a project board with stages such as Backlog, Ready, In Progress, In Review, QA, and Done, and pull requests are expected to include an issue link, clear acceptance criteria, and the required review before merge. This supports accountability, reduces handoff friction, and keeps delivery focused on small, testable increments.

The process also makes role clarity and communication explicit. Product, project, engineering, QA, and stakeholder responsibilities are defined so teams can align quickly and escalate risks appropriately. Communication happens through regular standups, weekly PM/PdM syncs, milestone reviews, and structured status updates, while risks and dependencies are tracked and escalated according to impact. Quality is treated as a continuous practice: teams run CI, security scans, smoke tests, unit and integration tests, and manual QA when needed before release.

After a release or milestone, OctoAcme captures learning in retrospectives and converts those lessons into action items with owners and due dates. This closes the loop from delivery back into process improvement, helping teams adapt, reduce inefficiency, and keep project execution consistent over time.

## How to use these docs

Use the overview document for a high-level understanding of the operating model, then move to the specific lifecycle document needed for your current work. For example, start with initiation when evaluating a new idea, planning when turning scope into a backlog, execution for day-to-day tracking, and release or retrospective docs when moving toward deployment and learning.
